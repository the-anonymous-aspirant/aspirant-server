- **Invoices: six small inconsistencies in the invoicing server** (system_3
  #12273).
  - **IBAN check digits:** an IBAN with check digits 00, 01 or 99 passes the
    mod-97 sum but no real IBAN has them. A client's IBAN like that is now
    refused (`invalid_iban`), and an N26 row carrying one is offered without
    it, as for any IBAN that fails the check. A client's Save does not check
    the IBAN it sends unchanged, so a client stored with one keeps saving its
    other fields.
  - **Fee sign:** every answer carries a payment's `fee_cents` as a charge
    positive and a fee given back negative. PayPal rows were answered as the
    file prints them (a charge negative), N26 rows as a charge positive.
    Stored rows are not rewritten: the sign is turned where the answer is
    built.
  - **Merged PDF audit:** the audit row counts the invoices merged, not the
    ids sent (`?ids=41,41,41` merges one).
  - **An expense's client:** `PATCH /invoicing/expenses/:id` changes or
    clears (`null`) `client_id` on an expense entered by hand, as the create
    sets it. It was refused, so a client set on create could never change.
  - **Removed transactions:** a removed payment or expense refuses an edit,
    and a receipt's replace or delete, with 409 `transaction_removed`, "This
    transaction was removed. Restore it to change it." Reading its receipt
    stays open.
  - **PayPal import:** the book is read once for the file instead of three
    times a row, and the new payments are stored in statements of up to
    1,000 rows, all in the one transaction, so a failure still stores
    nothing. In the tests a 2,500-row file ran 17,484 queries under the
    book's lock before, and runs a fixed few now.
